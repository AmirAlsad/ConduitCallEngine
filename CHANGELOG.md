# Changelog

## Unreleased

### Engine

- `.moment(.connected)` waits for CallKit's activation of the call's audio. A pre-connected ring answered with its agent there went to `.connected` at the answer and delivered the moment then, before CallKit had activated the session, so a host playing a sound on it played into a session that was not live; any call that connected before the activation did the same. The moment now comes once the call is connected, CallKit has activated its audio and it is not held, whichever is last: with the transition when the session is already active, otherwise at the activation (or the resume), with no state change. A call that drops before it was delivered gets `.moment(.connected)` instead of `.moment(.reconnected)` when it is back. Every other cue guarantee holds. **Behaviour change:** a host test that checks for `.moment(.connected)` must activate the session (`SimulatedCallSystem.activateAudioSession()`); for a ready answer the moment follows that activation, not the answer.

- Route work waits for CallKit's activation on every call, as it already did for a prepared one. A call that was not prepared and connected, or whose transport reported a route change, before CallKit activated the session (an answered call whose agent was quick, or a slow activation) read the routes and ran the hands-free default (an output-port override) on a session that was not active yet, and counted the default as applied. Now, while the session is not activated (before the first activation, and after a deactivation until the next), the engine reads no routes, applies no default and ignores `selectAudioDevice(_:)`; the activation refreshes the list and, for a connected call, applies the default. **Behaviour change:** `selectAudioDevice(_:)` before activation does nothing (it used to reach the transport), and a host test that checks routes after `.connected` must activate the session first.

- **Breaking:** a lost call-control signal is no longer permanent. The engine took `resumed` as heard the moment it queued it and never sent it again on a connection it believed healthy, so an agent that closed its audio on `call-held` stayed closed for the rest of the call if that one message was lost (Daily reported no delivery result; LiveKit gave up after its 2-second bound). `CallTransport.send(_:)` now returns a new `CallSignalDelivery` (`.sent`, `.failed`, `.unsupported`; the default implementation still drops the signal and returns `.unsupported`). After `.failed`, the engine sends the call's current state again (not the failed signal: a retry after the user resumed sends `resumed`, not `held`) after 1, 2, 4, 8, 16 and 30 seconds while sends keep failing, then waits for the next connection; the agent counts as possibly held until a `resumed` is `.sent`, so a reconnect sends `resumed` again until then. `answered` is retried the same way. A host transport that implements `send(_:)` must now return a result: `return .sent` reproduces the old behaviour (no retries). `send(_:)` is `@discardableResult`. `ConduitCallEngineTesting`: `FakeTransport.signalDeliveries`, the results its next sends return (`.sent` once empty).

- A pre-connection never makes an answered call worse than none. A `.media` ring whose transport joined and whose agent never came was not bounded during the ring, and at the answer the engine kept that agentless join, waited out `joinTimeout` with a ringback and failed the call as `.agentUnreachable`, where an unprepared answer would have fetched fresh credentials and reached a working agent. Now the ring's join is bounded by `joinTimeout`, counted from its `connect(_:)` returning: running out during the ring is a failed preparation (the ring rings on; an answer connects afresh, as before). And whatever the ring prepared failing after the answer, before the agent was there (the join's bound running out, its connect throwing, a drop, an error, rejected credentials, the agent leaving, or, at either tier, the ring's credential fetch failing) now sends the call down the unprepared path once: `connect` with `.answered`, then `connect(_:)` again on the same transport, which must take its earlier session over as on a reconnect attempt (no `disconnect()`, whose end-call signal could reach the agent of the room the fresh credentials name). The call stays `.connecting` with its ringback; if that connect fails too, the call fails as it would have without pre-connect. **Behaviour change:** a ring's credential failure after the answer used to fail the call at once; it now makes one `.answered` request first.

- A hold no longer lets the first connect's join deadline fail the call. A call held while it was still waiting for its agent failed as `.agentUnreachable` once `joinTimeout` ran out, with the user on another call; on Daily it always did, because a held call's agent audio is unsubscribed and Pipecat's Daily transport sends client-ready only for playable audio, so the bot could not become ready until the resume. A hold now stops that wait, a join that returns during the hold does not start it, and the resume starts it again in full. (A reconnect attempt's wait was already paused by the hold.) `ConduitCallEngineDailyTests` now also runs the real Daily adapter under a simulated engine, against Pipecat and Daily fakes whose readiness depends on the agent's audio subscription.

- Pre-connect: an incoming call can be prepared while it rings, so the agent is ready when the user answers. New `RingPreparation` (`.none`, `.credentials`, `.media`). The ring gets the lowest of what the push asks for (new push key `preconnect`, `"credentials"` or `"media"`; any other value or none is `.none`; the host sees it as the new `IncomingCall.requestedPreparation`), what the host's target allows (new `CallTarget.ringPreparation`, default `.none`, a new `init` parameter with that default), and, for `.media`, whether the transport can join while ringing (new `CallTransport.canConnectWhileRinging`, default `false`, which makes `.media` `.credentials`). With the push's or the host's opt-in missing, a ring behaves as before: nothing is fetched or created before the answer. Preparation starts once CallKit has accepted the ring's report. `.credentials` runs the target's `connect` during the ring with the new `ConnectRequest.Purpose.ringing(joinsBeforeAnswer:)` and keeps the result for the answer. `.media` also creates the transport (reading `canConnectWhileRinging` right after `makeTransport`) and joins during the ring with no attach, no mic and no route reads or changes; its events only advance the new observed `CallEngine.ringPreparationPhase` (`RingPreparationPhase`), never the call's `state`, which stays `.incomingRinging`. Answering a ring whose agent is there goes straight from `.incomingRinging` to `.connected(since:)` (the answer time) with `.moment(.connected)` and no `.start(.connecting)`; answering one still being prepared continues from where it is, without a second credential fetch. A prepared call refreshes routes and applies the hands-free default only once CallKit has activated the session. A failed preparation (credentials or join failing, or a drop, a rejected token or an error while joining) never ends the ring; the answer then connects as before, with a new transport and `.answered`. The agent leaving a ready ring (`.disconnected(reason: .botLeft)` before CallKit delivered an answer) ends it as the caller cancelling it: `.remoteEnded` to CallKit, a `CallRecord` with `missedReason: .canceledByCaller`, a `canceled` receipt, no cues. A ring that ends unanswered cancels a fetch in flight and disconnects the ring's transport (end-call signal if it is up). `"preconnect"` joins `CallEngine.supportedPushFeatures`.
- `CallSignal.resumed` is sent after the attach and mic commands of the resume have run, as `answered` already waited for the activation's, so it reaches an agent the user can hear. `held` still goes at once.

- `CallSignal.answered` is now sent, for every incoming call whose push carried `preconnect` (either value, also when the host allowed no preparation): once the call is answered, CallKit has activated its audio and the transport is connected, whichever comes last, after the attach and mic commands of that activation, again after every reconnect, and at the resume when the call is held then.
- **Behaviour changes with pre-connect:** a host that assumes every answered ring passes through `.connecting` sees `incomingRinging -> connected` for a ring answered with its pre-connected agent there; `makeTransport` can be called twice for one call (once for the ring, again at the answer if the preparation failed), so it must return a new transport each time; and with `.media` requested by the push and the target, the transport is created during the ring even when it then declares it cannot join.
- `ConduitCallEngineTesting`: `FakeTransport.canConnectWhileRinging` (settable, default false), `audioDeviceReadCount` and `audioDeviceSelections`. `SimulatedCallSystem.deliverTransportEvent(_:)` delivers to a ring's pre-connecting transport while the ring is being prepared.

- An engine reconnect attempt whose transport joins but never reports `.connected` no longer leaves the call in `reconnecting(attempt:)` for good. New `CallEngineConfiguration.joinTimeout` (default 30 seconds, `nil` for no bound): once an attempt's `connect(_:)` has returned without throwing, the engine waits that long for `.connected`; then the attempt counts as failed and the next one is scheduled with its backoff, or the call fails as `.lostConnection` when the retry budget is spent. A drop, a recovery, a hold or the end of the call during the wait stops it. The bound uses the engine's injected `sleep`. **Breaking for host tests:** with a `sleep` that returns at once, such a wait now ends on the engine's next suspension; pass `joinTimeout: nil` there.

- Documentation: `CallTransport`'s two synchronous requirements, `events` and `canConnectWhileRinging`, are nonisolated, so a main-actor conformer declares both `nonisolated` (only `events` was said). `ConnectRequest.Purpose` may gain cases in later versions; its documentation shows a `switch` that keeps compiling (`@unknown default`, which warns, naming the new case, when one is added). `CallTarget.makeTransport` is documented as called once per call, except a `.media`-prepared ring whose preparation failed before the answer, which makes a second.

- **Breaking:** `CallTarget.connect` takes a `ConnectRequest` (new): `purpose` (`.outgoing`, `.answered` or `.reconnect(attempt:)`) and, for an incoming call, the ring's `callID`, on every request including reconnects. A host's closure `connect: { ... }` becomes `connect: { request in ... }`, or `{ _ in ... }` to ignore it, and so does the `connect:` argument of `CallTarget.init`.

- An audio activation that arrives while a ring is unanswered is ignored. CallKit activates an incoming call's session only once its answer action is fulfilled, so such an activation belongs to an earlier call; it used to set `isAudioActivated` and attach the transport, and enable its mic, as soon as the answer created it, before CallKit had activated the session for the answered call. An activation after CallKit delivered the answer action, before the engine has handled it, still counts. **Behaviour change for host tests:** with `SimulatedCallSystem`, activate the session after `answerIncomingCall()`, not before it.

- When a reconnecting call recovers (the transport reports `.connected`) or is held while an engine reconnect attempt is inside the transport's `connect(_:)`, the engine no longer cancels that connect's task. It still cancels an attempt that is waiting out its backoff or fetching credentials, and ignores the outcome of a connect it leaves running. Cancelling it could abandon the session the call had just counted as connected: a transport may take its session over inside `connect(_:)`, and an SDK join that honours task cancellation (LiveKit's `Room.connect` checks it) cleans the room up when cancelled. `FakeTransport.cancelledConnectCount` (new) counts connects that finished with their task cancelled.

- A call whose agent never becomes ready no longer stays in `.connecting` until the user ends it. `joinTimeout` also bounds a call's first connect: when the transport's `connect(_:)` has returned and `.connected` does not follow within it, the call fails as `.agentUnreachable` (the first time the engine produces that reason), is ended in CallKit and recorded, and the transport is disconnected, which sends the end-call signal. **Behaviour change:** an agent that takes longer than 30 seconds to become ready after the device joins now fails the call; raise `joinTimeout` for it, or set it to `nil` for the 0.1 behaviour.

- Call hold. Calls are reported to CallKit as holdable (and as not groupable and without DTMF), and CallKit's hold action is handled, so a phone call the user takes or places during an engine call can hold it instead of ending it. New `CallEngineConfiguration.supportsHolding` (default `true`; `false` keeps calls unholdable, as before), `CallEngine.isOnHold`, and `CallEngine.setOnHold(_:)` for holding from the host's UI, which goes through CallKit like the system UI. The hold action applies only to the call it names, while it is connecting, connected or reconnecting; otherwise CallKit is told the action failed. Hold does not change `state`. While held the mic is closed (the mic rule gains "not on hold"), the engine calls `detachAudioSession()` and attaches again on resume once CallKit has the session activated, mute and push-to-talk changes are recorded for the resume, no cues are delivered, and a connection that drops waits at `reconnecting(attempt: 0)` without spending retries; on resume a paused reconnect starts at once at attempt 1. `.moment(.held)` and `.moment(.resumed)` are now delivered: hold stops a running loop first, and resume is followed by the loop the call's state wants (with `.moment(.connectionLost)` before it if the connection dropped during the hold). Held time counts toward `CallRecord.duration`. (Refs #2)
- New `CallSignal` (`answered`, `held`, `resumed`; raw values `call-answered`, `call-held`, `call-resumed`) and `CallTransport.send(_:)`, with a default implementation that drops the signal, so existing transports compile unchanged. The engine sends `held` and `resumed` while the transport is connected, `held` again after every reconnect of a held call, and `resumed` after a reconnect that follows a resume the agent missed. `answered` is sent for pre-connect (above). Both bundled adapters deliver them (see Transport adapters), and `send(_:)` reports a delivery result (above). (Refs #2)
- **Behaviour changes for hosts and transports with hold:** with the default configuration a phone call now holds the engine call instead of ending it, so a host sees `isOnHold` and the `.held`/`.resumed` moments where it used to see the call end; set `supportsHolding: false` to keep the old behaviour. A transport now gets `detachAudioSession()` on hold and `attachAudioSession()` on resume without a CallKit deactivation in between, and must stop and restart playout there.
- `ConduitCallEngineTesting`: `SimulatedCallSystem.setHeldFromSystem(_:onHold:)`, `holdRequests` (`HoldRequest`), `reportedSupportsHolding(_:)`, and `FakeTransport.sentSignals`. The simulated CallKit performs a requested hold through the engine for a call it holds that was reported holdable. (Refs #2)

- Incoming rings time out. A ring nobody answers or declines is ended after `CallEngineConfiguration.ringTimeout` (new, default 60 seconds, `nil` for no engine limit): CallKit is told `.unanswered`, the engine returns from `.incomingRinging` to `.idle`, the host gets a `CallRecord` (`outcome: .noAnswer`, `missedReason: .ringTimedOut`) and an `unanswered` receipt is sent when the push asked for receipts. A ring push may carry `ring_timeout` (whole seconds, as a string) to shorten its ring, never below 10 seconds and never beyond the configured timeout; it also applies when `ringTimeout` is `nil`. An answer CallKit has delivered always wins over the timer, even before the call connects. The timer runs on the engine's injected `sleep`. (Refs #3)
- Servers can withdraw a ring with a cancel push, `{"action": "cancel", "call_id": ...}` without `target_id`. It is reported to CallKit first under its `call_id`, like every VoIP push. For the call that is ringing and not yet answered, CallKit refuses the report as a duplicate and the engine ends the ring as `.remoteEnded`, returns to `.idle`, records it (`outcome: .noAnswer`, `missedReason: .canceledByCaller`) and sends a `canceled` receipt to the ring's `status_url`. For the call in progress it does nothing more. For an id the engine does not know, the report rings and is ended at once, with no record or receipt. Cancelled ids are remembered (the latest 32, for 10 minutes), so a ring that arrives after its own cancel is reported and ended at once without touching the engine. A push with any other `action` than `ring` or `cancel` is treated as malformed. (Refs #3)
- New `CallEngine.supportedPushFeatures` (`["cancel", "ring_timeout"]`, and `"preconnect"` with pre-connect, above), for hosts to send their server with the VoIP token so it uses these features only with devices that understand them.
- `MissedCallReason` gains `.ringTimedOut` and `.canceledByCaller`, a `reachedUser` property (true for those two, false for `.busy` and `.filteredByFocus`), and stable string raw values with `Codable`. **Breaking:** exhaustive switches over `MissedCallReason` need the new cases, and a host that treats every non-nil `missedReason` as a ring the user never saw should check `reachedUser`.
- New receipt statuses `unanswered` and `canceled`. Servers must accept statuses they do not know.
- Push contract: the `answered` receipt is sent at the answer, before iOS activates the call's audio, so it always precedes `call-answered`; the contract's advice to release a pre-connected agent's greeting on the receipt "if `call-answered` has not arrived" released it on every ring, into audio that was not up. A server should wait for `call-answered` and use the receipt only as a fallback, several seconds after both it and the device being in the room. The contract now says prominently to compare receipt `call_id`s case-insensitively, and that a server sending no `ring_timeout` must assume a ring can last indefinitely (an app may configure a longer ring timeout, or none).
- A ring CallKit refuses because it already holds a call with that id is no longer ended in CallKit (ending the id would end the call CallKit holds); it is still recorded as failed with `.unknown` and returns to idle.
- **Breaking for host tests:** the ring timeout uses the engine's injected `sleep`, so an engine built with a `sleep` that returns at once (as host tests often pass to `CallEngine.simulated`) now times out every ring on its next suspension. Pass `configuration: CallEngineConfiguration(ringTimeout: nil)` there.
- `ConduitCallEngineTesting`: the simulated CallKit now holds the ids of calls it has, and answers a report under a held id with `.duplicateCallID`, as CallKit does. **Breaking:** `SimulatedCallSystem.IncomingReportResult` gains `.duplicateCallID`.

- New cue events: `CallEngineDelegate.callEngine(_:cue:)` delivers a `CallCue` at each moment a host would mark with its own sound (`.start(.connecting)`, `.start(.retrying)`, `.stop`, and the one-shot `.moment(.connected)`, `.moment(.reconnected)`, `.moment(.connectionLost)`), and `CallEngine.repeatingCue` holds the loop that should be playing now. The engine guarantees every start is stopped before the next start, before a connected moment and by the time the call ends (provider reset included), one `connectionLost` per outage, and no cues for a ring that is never answered. `CallMoment.held` and `.resumed` mark call hold (above). `didChangeStateFrom:to:` is unchanged. Additive: the delegate method has a default implementation. The cues replace deriving sounds from transitions, which is what let a ringback run on after a provider reset. (Refs #5)

- The engine no longer waits indefinitely for a transport that reports `.reconnecting`. If neither `.connected` nor `.disconnected` follows within 30 seconds (the reconnection policy's backoff cap), the engine treats the transport as dropped and runs its own reconnect (`reconnecting(attempt: 0) -> reconnecting(attempt: 1)`, fresh credentials from the target's `connect`, then `connect(_:)` on the same transport instance, no `disconnect()`), which fails the call as `.lostConnection` if the outage outlasts the retry budget. On a device a stalled self-heal showed as a long silent gap before the call finally failed. With the bundled adapters, those attempts do not rejoin a session whose SDK is still healing it (LiveKit still reconnecting the room, or Daily's client still in the call): each such `connect(_:)` throws, so the attempt fails and spends a retry, and the SDK's own recovery still decides the outcome. Its completion reports `.connected` and the call recovers; its failure is reported as a drop, after which the next attempt joins afresh. Only a heal that outlasts the whole retry budget ends the call as `.lostConnection`. An attempt that runs once the SDK has already healed reports `.connected` itself.

- The mic is gated on audio activation and interruptions on every path. `setMuted(false)`, an unmute from the system call UI and `setPushToTalkActive(true)` used to open the transport's mic at once, even before CallKit activated the session or during an interruption, and the mic re-apply on `.connected` ignored interruptions. They now take effect only once the session is active and no interruption is in progress, and are applied when that becomes true. A push-to-talk button still held when the session activates or an interruption ends now opens the mic. (#19)

- The mic follows one rule whatever order its inputs arrive in. If CallKit activated the session again during an interruption and the interruption then ended without `shouldResume`, the mic stayed closed for the rest of the call while `isMuted` was false: the end of the interruption cleared `isInterrupted` without re-applying the mic. Every input (activation, deactivation, the start and end of an interruption, in-app and system mute, push-to-talk, the transport reporting `.connected`) now re-derives the mic, and the engine's attach, detach and mic commands reach the transport one after another in the order they were issued. A deactivation now also turns the mic off before detaching, and the transport reporting `.connected` before CallKit activated the session now gets `setMicEnabled(false)` (it got nothing). **Behaviour change:** after an interruption that ends without `shouldResume` and before CallKit activates the session again, `isInterrupted` stays true (it went false while the mic stayed closed); an unmute or a push-to-talk press in that state reopens the mic. `isInterrupted` is now a computed property.

- Once `startPushRegistration()` has run, the engine keeps itself alive for the rest of the process (its PushKit registry holds it strongly). Before, a host that released the engine left PushKit's callback with nothing to report the call, and iOS terminates an app that does not report a VoIP push. (#17)

- `TransportError.authenticationFailed` during a reconnect attempt (thrown by the target's `connect` or by the transport's), and an `.error(.authenticationFailed)` event while reconnecting, now fail the call at once as `.badToken`. They were retried like any other failed attempt until the budget ran out and the call failed as `.lostConnection`. (#11)

- Audio activation is tied to the call in progress. An activation that arrives with no call in progress (from a call that ended while dialing) is ignored instead of being replayed onto the next call's transport before CallKit activates that call, and `isAudioActivated` is cleared when a call ends. Deferred work started by an activation, a deactivation, a system mute, an interruption, a route change or a device-list refresh now acts on the transport that was live when it started and stops if that call has ended, instead of looking up whichever transport is current when it runs. (#9)

- Ring-status receipts are sent only for targets the delegate resolves. A push for an unknown target that was busy, filtered by Focus, or declined before CallKit accepted it used to POST to the push-supplied `status_url` with no bearer. For a push during another call, `targetForIncomingCall` is now asked whether or not CallKit accepted the report. (#8)

- A push carrying the `call_id` of the call that is ringing or in progress is treated as a duplicate delivery: it is reported to CallKit, as PushKit requires, and otherwise ignored. It used to take the busy path, producing a missed-call record and a `busy` receipt for a call that was ringing or live. (#7)

- CallKit answer and mute actions now apply only to the call they name. An answer for a busy ring that CallKit still showed answered the ringing call, and a mute for another call's id muted the live one. (#6)

- A CallKit provider reset now ends the call the way any other failure does: a call that is dialing, connecting, connected or reconnecting moves to `.failed(.unknown)` (so a host's transition-driven cues stop) and a ringing call returns to `.idle`; both produce a `CallRecord` (`outcome: .failed`, `failureReason: .unknown`). Before, the engine went to `.idle` with no terminal transition and no record. Nothing is reported back to CallKit, which has already ended the call, and no receipt is sent. (#5)

- A ring for a target the delegate does not resolve, or one CallKit refuses for a reason other than Focus, now returns from `.incomingRinging` to `.idle` instead of entering `.failed(.unknown)`, an active state that put a failure screen up for a ring the user never answered. It is still ended in CallKit and recorded (`outcome: .failed`, `failureReason: .unknown`). (#4)

- A call the remote party leaves before it connects now ends in `.ended(.noAnswer)`, matching its `CallRecord`; it was `.ended(.completed)`. An incoming call the user answers and then ends before it connects is now `.canceled` in both state and record; it was `.declined`, which is now kept for a ring the user declines. The outcome in `.ended(_)` is always the record's outcome. (#1)

### Transport adapters

- `ConduitCallEngineDaily` declares its dependency on Daily's `Daily` product (`daily-client-ios`, from 0.38.0, the floor `pipecat-client-ios-daily` already sets), which it imports directly and reached only through the Pipecat Daily package before. Nothing resolves differently.

- `PipecatDailyTransport.attachAudioSession()` returns once Daily has applied the subscription it asks for (within 2 seconds), instead of starting the change and returning, so a signal the engine sends after the attach (`call-answered`, `call-resumed`) cannot reach the agent before the user can hear it. The experimental ring-join strategies (SPI only) also count the bot's presence as ready only for a join made while they hold the agent's audio back (before the transport's first attach): an outgoing call, which CallKit activates before it joins, and a reconnect after the answer wait for bot-ready, as without the switch, instead of opening the mic before the bot can hear the user. An outgoing call on such a transport that joins before CallKit activates it still counts presence, as it cannot get the bot ready until the attach.

- `LiveKitTransport` reports `.disconnected(reason: .botLeft)` when the last remote participant leaves this attempt's room after it started connecting and before the agent was reported ready (an agent that came with LiveKit's join response and left before the room connected). It reported nothing, so a pre-connected ring kept a room with no agent (the push contract says such a preparation is dropped) and a call waited out `joinTimeout`. **Behaviour change:** such a call the user placed now ends as `.noAnswer` at once instead of failing as `.agentUnreachable` 30 seconds later, as on Daily. A join the transport supersedes no longer reports its room's participants leaving as the agent's hangup.

- `LiveKitTransport` owns its joins. LiveKit's `Room.connect` cleans up and sets the room up before the room reports `.connecting`, and `Room.disconnect` does nothing while the room is `.disconnected`, so a `disconnect()` in that window (a ring declined, or a call ended, just as the device started joining) sent nothing and left nothing, and the join then completed with no owner: the device stayed in the room with the agent. `disconnect()` now lets a join in flight finish (within its 2-second bound) before it signals and leaves, and a join it could not wait for leaves the room, with the end-call signal, when it completes. And a `connect(_:)` while an earlier join was still in flight (a quick hold and resume during a reconnect attempt's join) started a second `Room.connect` on the same room, each one's cleanup tearing the other down; it now cancels the earlier join and waits for its cleanup first. Internally the transport now reaches `Room` and LiveKit's audio engine through two small seams, so `ConduitCallEngineLiveKitTests` runs the real adapter under a simulated engine against a room double that sequences its work as LiveKit's does.

- `PipecatDailyTransport.connect(_:)` takes over a session whose bot never got ready instead of refusing it. After a reconnect attempt's join deadline ran out, the engine connects the same transport again, usually with fresh credentials for another room, while the Pipecat client is still joined to the stale one; the adapter refused that because the client was "still in the call", so every remaining attempt threw (each one stranding a newly started agent on a backend that starts one per request) until the call failed as `.lostConnection`. The resume after a held reconnect hit the same refusal. Such a connect now leaves the stale session without the end-call signal, releases its client (so its late callbacks reach nothing) and joins with a new client. A call Daily is healing (connected, with the network path down) is still refused, as before, so Daily's own recovery is not discarded.

- Both adapters report what became of a call-control signal (`CallSignalDelivery`). `LiveKitTransport.send(_:)` returns `.sent` once LiveKit took the message on its reliable data channel, and `.failed` when the room was leaving or gone, the publish failed, or its 2-second bound ran out. `PipecatDailyTransport.send(_:)` now sends through the Daily call client's `sendAppMessage(json:to:)` (the call Pipecat's transport makes, with `completion: nil`) in the form that reports Daily's result, so it returns `.sent` once Daily has sent the message and `.failed` before the join, after `disconnect()` or when Daily refuses it. The end-call signal is sent as before.
- Both adapters deliver call-control signals: `send(_:)` carries each `CallSignal` as the end-call signal's RTVI client message with the signal's raw value as `t` (`{"id": "<8 characters>", "label": "rtvi-ai", "type": "client-message", "data": {"t": "call-held"}}`; Daily's also carries `"d": null`, as its end-call signal always has). Neither throws or retries; a signal for a connection that is gone is dropped and logged. (Refs #2)
- `LiveKitTransport` publishes its client messages reliably. The end-call signal used LiveKit's default data options, which are lossy and can drop a packet under backpressure.
- `PipecatDailyTransport` sends its client messages, the end-call signal included, once the Daily call is joined, through the Pipecat transport's Daily app message. It used `PipecatClient.sendClientMessage`, which refuses until the bot has reported ready, so a hangup from a call whose bot was not ready yet sent no end-call signal and the agent waited out its grace window.
- Held calls are silent on both adapters. `PipecatDailyTransport`'s `attachAudioSession()` and `detachAudioSession()` did nothing, so a held Daily call could keep playing the agent; a detach that follows an attach now unsubscribes from the agent's audio (Daily has no playout control) and the next attach subscribes again, and a held call that reconnects joins unsubscribed. A call that is never detached keeps Daily's default subscription. `LiveKitTransport` already stopped playout and capture on detach by disabling LiveKit's audio engine; it now logs the engine state on attach, detach and connect. Daily's behaviour is pending device verification. (Refs #2)
- Both adapters declare `canConnectWhileRinging`: `true` on `LiveKitTransport`, which touches no audio before the attach; `false` on `PipecatDailyTransport`, whose media-tier support is pending device verification.

- Both adapters treat a connect attempt as over once it has reported a disconnect, its connect has thrown, or the host has called `disconnect()`, and report nothing that would steer the engine after that. Previously the attempt's state was only reset when the next `connect` ran, which is after the host's credential code, so a late callback from the dropped call was judged as part of a live one: on LiveKit a late participant-left could end a reconnecting call as `.completed`, and on Daily a late bot-left could do the same, a late bot-ready could report a dead attempt as connected, and a failed reconnect attempt was counted twice (its connect threw and the Pipecat client also reported `.disconnected`). Neither adapter reports `.connected` after the host's `disconnect()` any more. ([#10](https://github.com/AmirAlsad/ConduitCallEngine/issues/10))
- `PipecatDailyTransport.disconnect()` now releases its Pipecat client after sending the end-call signal and leaving. It never did, so every Daily call left Pipecat's `DailyTransport` and its Daily `CallClient` alive for the rest of the process: the transport holds its client options, whose `transport` is the transport itself, and pipecat-client-ios-daily 1.3.0 breaks that cycle only in `release()`. A `connect` after `disconnect()` now builds a fresh client (before, it reused the old one), and a `connect` that starts while a `disconnect()` is still flushing its end-call signal gets its own client, which that disconnect does not touch.
- `LiveKitTransport.disconnect()` sends the end-call signal whenever the room is not already leaving, not only once it reports connected. A host that disconnected while its connect was still in flight, or during one of LiveKit's own reconnects, sent nothing, so the agent waited out its grace window. The adapter now lets an in-flight connect finish before it publishes, and bounds the whole signal at 2 seconds so a hangup never waits on a room that will not come back. ([#22](https://github.com/AmirAlsad/ConduitCallEngine/issues/22))
- `PipecatDailyTransport.connect(_:)` no longer breaks a call that Daily is healing. When a lost network path is not back within 30 seconds, the engine runs its own reconnect on the same transport while the Pipecat client is still in the call; Pipecat refuses that connect (`BotAlreadyStartedError`), and the adapter used to reset its connection state and stop watching the network path first, so nothing was left to report the path coming back or Daily recovering: every later attempt failed the same way and the call ended as `.lostConnection` even after Daily had healed. A connect on a client that is still in the call now changes nothing: it reports `.connected` if the call is connected and the path is up, and otherwise throws `.connectionFailed` and leaves the path watch running, so the path coming back recovers the call and a Daily disconnect is still reported as a drop. A connect that arrives while an earlier join is still waiting for the bot no longer swallows that join's bot-ready either.
- `LiveKitTransport.connect(_:)` no longer rejoins a room LiveKit is still reconnecting. The engine runs its own reconnect on the same transport when LiveKit's has not finished within 30 seconds, and `Room.connect` began by cleaning the room up, which ended LiveKit's reconnect state without cancelling its reconnect task. The cleanup reported the reconnect complete with the room not connected, which the adapter took as a drop of the brand-new attempt (spending a retry and cancelling it), and the surviving task could later mark the room connected while the next join was still under way, after which that join never reported `.connected` and the call could sit in `reconnecting` with the mic off. Such a connect now throws `.connectionFailed` and leaves LiveKit's reconnect to report its outcome; a room that has already healed with the agent present is reported `.connected`; and a reconnect completion that arrives before the current attempt's room has connected is ignored.
- `LiveKitTransport` classifies a connect error as `.authenticationFailed` only on an exact signal: LiveKit's validation request answered 401 or 403 (a `.validation` error whose message starts `HTTP 401:` or `HTTP 403:`), or LiveKit's insufficient-permissions error. It used to search the error's whole description for "unauthorized", "401", "permission" or "token", and that description includes nested errors' user info, such as the failing WebSocket URL with its encoded join request, so a plain network failure could match by chance, and a server host name containing "token" always did. With the engine now ending a reconnecting call at once on `.authenticationFailed`, such a false match would have ended a call that only needed a retry.
- The LiveKit dependency floor is now 2.18.0 (was 2.15.1). From 2.18.0 every reconnect LiveKit gives up on ends with the room disconnected (client-sdk-swift PR #1144); before it, a failed full reconnect could be reported as complete with the room still marked connected, and the call could show connected with no audio. A server-ordered full reconnect whose media connection times out is now retried by LiveKit and then reported as a drop. The adapter no longer disconnects the room itself after a completed reconnect, which only older versions needed. ([#20](https://github.com/AmirAlsad/ConduitCallEngine/issues/20))
- A LiveKit reconnect that rejoins a room with no remote participant now ends the call as the agent's hangup (`.disconnected(.botLeft)`, so `ended(.completed)`), instead of reporting a network drop that made the engine run the target's `connect` again and, on a typical backend, start a fresh agent session inside the same call. The agent left while the device was offline; this matches what already happened when the agent left a connected call or when a quick reconnect delivered its departure. ([#21](https://github.com/AmirAlsad/ConduitCallEngine/issues/21))

## 0.1.0 - 2026-11-11

- Initial extraction of the call engine from the Conduit iOS app. `ConduitCallEngine` provides `CallEngine`, which reports calls to CallKit, receives agent-initiated calls over PushKit VoIP pushes, runs the call state machine, owns the call's audio-session policy and reconnects after drops, driven by host-supplied `CallTarget` values and reporting back through `CallEngineDelegate` and `CallRecord`. It also sends optional ring-status receipts and defines the `CallTransport` protocol.
- `ConduitCallEngineDaily` (`PipecatDailyTransport`, Daily through the Pipecat iOS client) and `ConduitCallEngineLiveKit` (`LiveKitTransport`, native LiveKit with manual audio) adapters, shipped as separate products so the core links no WebRTC SDK.
- `ConduitCallEngineTesting`: `FakeTransport`, `SimulatedCallSystem` and `CallEngine.simulated(...)` for the iOS Simulator and host unit tests.
- `PipecatDailyTransport` reports short network interruptions: while connected, losing the device's network path emits `.reconnecting` (the call shows `reconnecting(attempt: 0)`) and getting it back emits `.connected`, as LiveKit's own reconnects already did. Daily heals these inside its SDK without telling the Pipecat client, so they were silent before. The signal is the network path, not Daily's media state.
- `LiveKitTransport` no longer reports a call connected after LiveKit abandons its own reconnect. A completed SDK reconnect now counts only if the room is connected and a remote participant is present; otherwise the adapter disconnects the room and reports `.disconnected(.networkDropped)`, so the engine's reconnect and retry budget apply. Previously a long outage could leave the call showing connected with no audio and no further recovery.
