# Changelog

## 0.2.0

0.2 adds pre-connect (preparing an incoming call while it rings), ring timeouts and cancel pushes, call-control signals to the agent (among them `call-connected`, which tells the agent when to start speaking), sound cues, a minimum time a call the user placed shows as connecting, a bound on how long a call waits for its agent, and a log hook, with call hold as an experimental opt-in that is off by default; makes the public API usable from a Swift 6 host; lets a host test drive every feature deterministically; and fixes many ordering and recovery bugs found on devices, in both adapters and the engine. A 0.1 host needs a few source changes and should read the behaviour changes below: several defaults now do something 0.1 did not (rings time out, a call whose agent never comes fails, the mic opens only once the call is connected). A phone call the user accepts during a call still ends it, as in 0.1.

### Breaking changes and how to migrate from 0.1

Work through these in order; the first five are compile errors, the rest change what an unchanged host sees.

1. **`CallTarget.connect` takes a `ConnectRequest`.** It says why the engine asks (`purpose`: `.outgoing`, `.answered`, `.ringing(joinsBeforeAnswer:)` or `.reconnect(attempt:)`) and, for an incoming call, the ring's `callID`, on every request including reconnects. Change `connect: { ... }` to `connect: { request in ... }`, or `{ _ in ... }` to ignore it. `ConnectRequest.Purpose` is open: end a `switch` over it with `@unknown default`.
2. **`CallTarget.init` gains `ringPreparation:`**, between `handle:` and `makeTransport:`, defaulting to `.none`, and `handle:` now defaults to nil. A 0.1 call with every argument compiles unchanged; pass `ringPreparation:` before `makeTransport:` when you use it.
3. **`TransportError` loses `.timedOut` and `.botUnavailable`**, which nothing produced and the engine treated as any other failure. Throw or emit `.connectionFailed("...")` instead.
4. **`MissedCallReason` gains `.ringTimedOut` and `.canceledByCaller`**, string raw values, `Codable`, and `reachedUser` (true for the two new reasons, false for `.busy` and `.filteredByFocus`). Handle the new cases in a `switch` (it is open: end it with `@unknown default`), and if you treat every missed ring as one the user never saw, check `reachedUser`.
5. **`ConduitCallEngineTesting`.** `FakeTransport` is now a `@MainActor` class: read and configure it from the main actor (its `init`, `emit(_:)`, `finish()` and `canConnectWhileRinging` work from anywhere). `SimulatedCallSystem.IncomingReportResult` gains `.duplicateCallID`. Each simulated outgoing call now gets a CallKit id of its own (they all shared one), so read the id from `startedCallIDs` instead of assuming the first call's.
6. **Rings time out.** An unanswered ring ends after `CallEngineConfiguration.ringTimeout` (default 60 seconds) as missed (`.ringTimedOut`). Set `ringTimeout: nil` for 0.1's unlimited ring.
7. **A call whose agent never comes fails.** `joinTimeout` (default 30 seconds) bounds the wait for `.connected` after the transport's `connect(_:)` has returned: a call's first connect then fails as `.agentUnreachable`, and a reconnect attempt counts as failed. Raise it for an agent that takes longer to become ready, or set it to nil for 0.1's unbounded wait.
8. **Phone calls: no change.** `supportsHolding` defaults to false, so a 0.1 host sees no change in what a phone call does: the engine's call is reported as not holdable, a phone call the user accepts or places during it ends it, and the engine tears down as for any end, sends the end-call signal and delivers one record. Call hold is experimental ([below](#experimental-call-hold-off-by-default)); do not turn it on in a shipping app. A host that does, and has a custom transport, must stop and restart playout on `detachAudioSession()` and `attachAudioSession()`, which a hold calls without a CallKit deactivation between them (Integration Guide, section 12).
9. **Custom transports.** If you write a `CallTransport`: `send(_:)` (new, optional) returns a `CallSignalDelivery`. A `send(_:)` that returns nothing does not implement the requirement, so the engine silently uses the default, which drops every signal; return `.sent`, `.failed` or `.unsupported`. A main-actor transport declares `canConnectWhileRinging` `nonisolated`, as it does `events`; a transport that joins differently during a ring can implement the new `connectWhileRinging(_:)` (optional; the default calls `connect(_:)`). And `connect(_:)` must handle a session that is still up (report `.connected`, take the session over, or throw without disturbing an SDK that is healing it), because the engine now reconnects on the same instance when a transport's own healing stalls or a join never reports `.connected`; see "`connect(_:)` must handle a session that is still up" in section 12.
10. **Outcomes.** A call the remote party leaves before it connects ends in `.ended(.noAnswer)` (was `.completed`); an incoming call the user answers and then ends before it connects is `.canceled` (was `.declined`, now kept for a declined ring). A ring for an unknown target, or one CallKit refuses for a reason other than Focus, returns from `.incomingRinging` to `.idle` (it entered `.failed(.unknown)`), still with a record. A CallKit provider reset fails a live call as `.failed(.unknown)` and records it (it went to `.idle` with no record). `.ended(outcome)` and the call's record always agree.
11. **Host tests.** The ring timeout, `joinTimeout`, `micWithholdTimeout` and `minimumOutgoingConnectingDuration` (zero unless you set one) run on the `sleep` given to `CallEngine.simulated`, so with a `sleep` that returns at once every ring times out and every call waiting for its agent fails, on the engine's next suspension: keep the default real-time `sleep` and end the timer you want with the new `SimulatedCallSystem.fireTimer(_:)`, or pass `CallEngineConfiguration(ringTimeout: nil, joinTimeout: nil)`. Activate the audio session (`activateAudioSession()`) after `answerIncomingCall()`, not before: an activation during an unanswered ring is now ignored. A test that checks `.moment(.connected)`, routes or `selectAudioDevice(_:)` must activate the session first, and one that checks the mic must also deliver `.connected` (below).
12. **Servers.** Ring-status receipts carry `call_id` in lowercase (they were `UUID.uuidString`, uppercase), with the body's keys sorted; compare ids case-insensitively. When your app sends `IncomingCall.callID` or `ConnectRequest.callID` to your server, write `uuidString.lowercased()` to match. Servers must accept receipt statuses they do not know (`unanswered` and `canceled` are new).
13. **Calls start on the earpiece.** The engine no longer moves a call with nothing connected to the loudspeaker: it makes no route change of its own, so a call starts where iOS puts it (the earpiece, with nothing connected), like a phone call. A 0.1 host that relied on the speaker default must set `defaultsToSpeaker: true` in `CallEngineConfiguration`, which applies it exactly as 0.1 did. (Refs #13)
14. **LiveKit 2.18.0 or later** is required (was 2.15.1); see the LiveKit fixes.

Then, recommended rather than required: give every `switch` over an open enum an `@unknown default` (Integration Guide, "Switching over the engine's enums"); a `CallCue` switch that matches `.moment(...)` or `.start(...)` payloads counts.

### Added

**Calls**

- **Diagnostics after a real interruption.** At the attach that follows an `AVAudioSession` interruption that was in progress while the call's media was detached (CallKit's deactivation, or a hold), the engine logs the audio session (category, mode, options, other audio, the hint to silence secondary audio, sample rate, input availability, route), and again a second and three seconds later. `FakeTransport` records every attach, detach, mic command and signal in order (`commands`).
- **An attach whose audio did not start is retried.** New optional `CallTransport.audioStartFailure()` (default nil). After each attach the engine asks it; for a failure it attaches again after 0.5, 1 and 2 seconds while the call stays activated, attached and not held, and `call-connected` (and, with the experimental hold, `call-resumed`) waits until the audio started or those attempts are spent (logged as an error). `LiveKitTransport` reports a start of its audio engine that LiveKit refuses, with the engine's and the session's state in the log, and takes the engine down before the next attach. `FakeTransport.failingAttaches` makes attaches fail.
- **Pre-connect.** An incoming call can be prepared while it rings, so the agent is ready when the user answers. New `RingPreparation` (`.none`, `.credentials`, `.media`): the ring gets the lowest of what the push asks for (new key `preconnect`, `"credentials"` or `"media"`, seen by the host as `IncomingCall.requestedPreparation`), what the target allows (`CallTarget.ringPreparation`, default `.none`) and, for `.media`, whether the transport can join while ringing (new `CallTransport.canConnectWhileRinging`, default `false`, which makes `.media` `.credentials`). With any of them at none, a ring is exactly what it was. Preparation starts once CallKit has accepted the ring's report. `.credentials` runs the target's `connect` during the ring (`.ringing(joinsBeforeAnswer: false)`) and keeps the result for the answer; `.media` also creates the transport and joins during the ring (`.ringing(joinsBeforeAnswer: true)`) with the new `CallTransport.connectWhileRinging(_:)` (optional: its default calls `connect(_:)`; every later connect of the call is `connect(_:)`), with no attach, no mic and no route reads or changes, its join bounded by `joinTimeout`. The new observed `CallEngine.ringPreparationPhase` (`RingPreparationPhase`) says how far it got; `state` stays `.incomingRinging`. Answering a ring whose agent is there goes straight to `.connected(since:)` with `.moment(.connected)` and no `.start(.connecting)`, and sets the new `ActiveCall.wasReadyAtAnswer`; answering one still being prepared continues from where it is and connects the moment its agent is there. A failed preparation never ends the ring, and never makes the answered call worse than none: before the answer, the answer connects as without pre-connect (a new transport, `connect` with `.answered`); after it, before the agent was there, the call makes one unprepared `.answered` request and connects the same transport again with it, which must take its earlier session over. The agent leaving a ready ring before the answer ends it as the caller cancelling it (`.remoteEnded`, `missedReason: .canceledByCaller`, a `canceled` receipt, no cues). A ring that ends unanswered cancels a fetch in flight and disconnects the ring's transport. `"preconnect"` joins `CallEngine.supportedPushFeatures`.
- **Minimum connecting time for calls the user placed.** New `CallEngineConfiguration.minimumOutgoingConnectingDuration` (default zero): an outgoing call whose transport reports `.connected` sooner stays `.connecting` until that long has passed since `.start(.connecting)`, so a host's ringback plays its first tone in full and the state, CallKit's connected report, `.stop` and `.moment(.connected)`, the mic, `call-connected` and the record's duration (counted from the reported connection) agree. It never applies to an incoming call: an answered call becomes `.connected` as soon as its transport is ready, and a pre-connected ring answered with its agent there goes straight to connected. While the engine holds a ready connection, the transport's readiness has already ended the `joinTimeout` wait; what the transport reports about the connection (a drop, healing itself, the agent leaving, rejected credentials, a connect that throws) is applied to the call it made, which is reported connected first, so the call ends where it would have without the minimum; ending the call is `.canceled` (never connected), a provider reset fails it, a hold stops the wait and the resume starts it again in full, and mute, interruptions and a deactivation change only the mic. New `EngineTimer` for it in the Testing product: `fireTimer(.minimumOutgoingConnectingDuration)`.
- **Ring timeout.** New `CallEngineConfiguration.ringTimeout` (default 60 seconds, nil for no engine limit): an unanswered ring is ended in CallKit as `.unanswered`, recorded (`outcome: .noAnswer`, `missedReason: .ringTimedOut`), sent an `unanswered` receipt when the push asked for receipts, and the engine returns to `.idle`. A push may carry `ring_timeout` (whole seconds, as a string) to shorten its ring, never below 10 seconds and never beyond the configured timeout; it also applies when `ringTimeout` is nil. An answer CallKit has delivered always wins over the timer. (Refs #3)
- **Cancel pushes.** A server can withdraw a ring with `{"action": "cancel", "call_id": ...}` (no `target_id`). It is reported to CallKit under its `call_id` first, like every VoIP push. For the call that is ringing and not answered, CallKit refuses that report as a duplicate and the engine ends the ring as `.remoteEnded`, returns to `.idle`, records it (`outcome: .noAnswer`, `missedReason: .canceledByCaller`) and sends a `canceled` receipt. For the call in progress it does nothing more; for an id it does not know, the report rings and is ended at once, with no record or receipt. Cancelled ids are remembered (the latest 32, for 10 minutes), so a ring that arrives after its own cancel is reported and ended at once. A push whose `action` is neither `ring` nor `cancel` is malformed. (Refs #3)
- **`CallEngine.supportedPushFeatures`** (`["cancel", "ring_timeout", "preconnect"]`), for hosts to send their server with the VoIP token so it uses these features only with devices that understand them.
- **Join timeout.** New `CallEngineConfiguration.joinTimeout` (default 30 seconds, nil for none): once a transport's `connect(_:)` has returned, the agent has that long to be ready (`.connected`). On a call's first connect the call then fails as `.agentUnreachable` (the first time the engine produces that reason), is ended in CallKit, recorded and disconnected; on a reconnect attempt the attempt counts as failed and the next one follows its backoff, or the call fails as `.lostConnection` when the budget is spent; on a ring's join the preparation fails. A drop, a recovery, a hold or the end of the call stops the wait.
- **Call-control signals.** New `CallSignal` (`connected`, `held`, `resumed`; raw values `call-connected`, `call-held`, `call-resumed`) and `CallTransport.send(_:)`, which returns a new `CallSignalDelivery` (`.sent`, `.failed`, `.unsupported`); its default implementation drops the signal and returns `.unsupported`, so a 0.1 transport compiles unchanged. On every call, placed or answered, the engine sends `connected` (the user is on the line; an agent should greet on it, not when the session connects) once the call is connected, CallKit has activated its audio, it is not held and the host is not withholding the mic, whichever comes last, and again on every new connection after a reconnect; mute and push-to-talk do not delay it, and a call that connects while held gets it after `resumed`, and after the resume's `.moment(.connected)`, so a withhold made inside that cue holds it back. With the experimental hold on (`held` and `resumed` are never sent otherwise), it sends `held` and `resumed` once the call's transport has joined, also while the call still shows connecting (waiting for its agent, or for the outgoing minimum with the agent there), a hold before the join at the join, `held` again after every reconnect of a held call, and `resumed` after a reconnect that follows a resume the agent may have missed; on a new connection the hold state goes before `connected`. `resumed` waits for CallKit's activation of the resumed call's audio; `resumed` and `connected` go after the attach and mic commands issued before them; `held` goes at once. After `.failed`, the engine sends the call's current state again (not necessarily the failed signal) after 1, 2, 4, 8, 16 and 30 seconds while sends keep failing, then waits for the next connection; the agent counts as possibly held until a `resumed` is `.sent`. `.unsupported` is never retried. Both bundled adapters deliver the signals (below). (Refs #2)
- **Cues.** `CallEngineDelegate.callEngine(_:cue:)` delivers a `CallCue` at each moment a host would mark with its own sound: `.start(.connecting)`, `.start(.retrying)`, `.stop`, and the one-shot `.moment(.connected)`, `.moment(.reconnected)`, `.moment(.connectionLost)`, and, with the experimental hold, `.moment(.held)` and `.moment(.resumed)`; `CallEngine.repeatingCue` holds the loop that should be playing now. Every start is stopped before the next start, before a connected moment and by the time the call ends (provider reset included); there is one `connectionLost` per outage; a ring that is never answered gets no cues; `.moment(.connected)` comes only once CallKit has activated the call's audio and the call is not held. The cues replace deriving sounds from transitions, which is what let a ringback run on after a provider reset. Whether to make a sound is the host's choice: `CallEngine.activeCall` is set at every cue, its `direction` tells a placed call from an answered one, and the new `ActiveCall.wasReadyAtAnswer` tells an answered call whose pre-connected agent was already there (no `.start(.connecting)`; its `.moment(.connected)` comes at the answer or at CallKit's activation) from one that had to connect, so a host can play a ringback only for calls the user placed and stay silent for a call ready at the answer. (Refs #5)

**Host integration**

- **`CallEngineConfiguration.defaultsToSpeaker`** (default false): whether the engine moves a call to the loudspeaker, once per call after CallKit's activation, when the transport lists no Bluetooth or wired route, the hands-free default 0.1 always applied. Off, the engine makes no route change of its own; the user's picker, the system call screen's route button, Bluetooth and CarPlay behave as before, and a route the user picked survives reconnects and holds. This is the configurable hands-free policy deferred from 0.1. (Refs #13)
- **Mic withhold.** New `CallEngine.setMicWithheld(_:)`, observed `CallEngine.isMicWithheld` and `CallEngineConfiguration.micWithholdTimeout` (default 5 seconds), for a host that plays its own sound into the call when it connects (a spoken "Connected") and does not want the agent to hear it through the mic. Withholding is one more input to the one mic rule: the mic is on only once the call is connected and while the session is activated, the call is not held, nothing interrupts it and the host is not withholding it, then following mute or push-to-talk. It is not mute (`isMuted`, CallKit's mute state and the system call UI do not change) and changes nothing but the mic and when `call-connected` is sent: the release sends it. It can be set at any time, before a call included, takes effect in any order with the other inputs, and is synchronous, so a withhold made inside `callEngine(_:cue:)` is in place before the engine's next mic command; releasing re-derives the mic from the rule. It ends with the call, however the call ends. Once the call is connected with its audio activated, the engine releases a withhold after `micWithholdTimeout` and logs a warning, so a host that never releases cannot leave the mic silently closed. A host that does not call it sees no change.
- `CallEngineDelegate.callEngine(_:didChangeRingPreparationPhaseFrom:to:)`: every real change of `ringPreparationPhase`, with the property already updated. The phase leaves `.idle` only while ringing, never with a state change; it returns to `.idle` before the answer's transition out of `.incomingRinging`, or after an unanswered ring's `didFinish`; the first change can come inside the push handling, when CallKit accepts the report.
- `CallEngineDelegate.callEngineDidInvalidateVoIPPushToken(_:)`: PushKit invalidated the token (0.1 only logged it); `voipPushToken` is nil until a new one is issued. (Refs #13)
- **Log hook.** New `CallEngineLog`: a `handler` that receives every event (`level`, `category`, `message`) the engine and both adapters log, instead of unified logging; `minimumLevel`, below which an event is dropped before its message is built; and `writeToOSLog(_:)`, for a handler that keeps Console output. Without a handler the output is what it was (same subsystem, categories and levels; debug and info only in debug builds of the package). Safe to use from any thread. No message carries a credential: URL queries, fragments and user info, bearer values, JSON Web Tokens and the values of token-like keys are removed from every message, including SDK and host error descriptions, before it is delivered. CallKit's raw audio activations, including the ones the engine ignores, are visible through it. (#18)
- `CallTarget` and `CallEngineConfiguration` are `Sendable`, and every public API works from a host built in the Swift 6 language mode with complete concurrency checking, without warnings, `@preconcurrency` or `nonisolated(unsafe)`; the package builds such a host as its `ConduitCallEngineSwift6Tests` target. (#14)
- `CallState.isConnected`. (#15)
- Every public enum says whether it is closed (no case added within a major version) or open (end a `switch` with `@unknown default`); see the Integration Guide. (#12)

**`ConduitCallEngineTesting`**

- `SimulatedCallSystem.awaitPendingWork()` waits until the engine has finished the work it started by itself (CallKit's activation, attach, detach and mic commands, signals, route refreshes, teardowns, the connect after a failed preparation) and what that work started; `fireTimer(_:)` runs one of the engine's timers out now (`EngineTimer`: `.ringTimeout`, `.joinTimeout`, `.transportHealTimeout`, `.reconnectBackoff`, `.signalRetry`, `.micWithholdTimeout`, `.minimumOutgoingConnectingDuration`, `.activationRecovery`). With them a host test drives every feature without sleeping or polling. (#15)
- `SimulatedCallSystem.awaitRingPreparation()`, which waits until the ringing call's preparation has done what it does by itself and returns `ringPreparationPhase`; `setHeldFromSystem(_:onHold:)`, `holdRequests` (`HoldRequest`) and `reportedSupportsHolding(_:)`; `invalidateVoIPPushToken()`. The simulated CallKit holds the ids of the calls it has, answers a report under a held id with `.duplicateCallID`, as CallKit does, and performs a requested hold through the engine for a call it holds that was reported holdable. `deliverTransportEvent(_:)` reaches a ring's pre-connecting transport while the ring is being prepared.
- `FakeTransport(reportsConnectedAfter:)`, which reports `.connected` by itself after each successful connect, for a simulator build (#15); `canConnectWhileRinging` (settable, default false), `ringingConnectCount` (joins made with `connectWhileRinging(_:)`, also counted in `connectCount`), `sentSignals`, `micEnabledHistory` (every value the engine passed to `setMicEnabled(_:)`, in order), `signalDeliveries` (the results its next sends return; `.sent` once empty), `audioDeviceReadCount`, `audioDeviceSelections`, and `canceledConnectCount` (connects that finished with their task cancelled).

### Experimental: call hold (off by default)

Do not enable it in a shipping app yet. Device tests on an iPhone 17 with iOS 27.0, with the bundled Daily and LiveKit transports: in-app hold and resume with no other call restored two-way audio on both, every time it was tried. Resuming after a real phone call did not: iOS held the call, the engine resumed it when the phone call ended and CallKit reported `didActivate` with the session in `playAndRecord` / `voiceChat`, but no audio returned in either direction. On LiveKit, making the audio engine available failed with `LiveKitError` code 801, "Audio engine returned error code: -4010", on every attempt for at least six seconds; on Daily no error surfaced and the audio was simply absent, and a second in-app hold and resume and a route change did not help. iOS delivered no interruption-ended notification in any run. Observations from a single run each, not conclusions: on Daily, leaving the room without the end-call signal and joining it again on a fresh client restored two-way audio after a phone call; on LiveKit, restarting the audio engine (at once, after a pause with retries, after telling WebRTC's audio session it was activated) failed with the same -4010; and on both, after the phone call ended, the system call screen still showed the call as held while the engine reported it resumed, which nobody has traced.

- **Call hold.** With `supportsHolding: true`, calls are reported to CallKit as holdable (and as not groupable and without DTMF), and CallKit's hold action is handled, for the call it names, while it is connecting, connected or reconnecting; otherwise CallKit is told the action failed. New `CallEngineConfiguration.supportsHolding` (default false), `CallEngine.isOnHold`, and `CallEngine.setOnHold(_:)`, which holds from the host's UI through CallKit, as the system UI does. Hold does not change `state`. While held the mic is closed, the transport is detached (and attached again on resume once CallKit has the session activated), mute and push-to-talk changes are recorded for the resume, no cues are delivered, a connection that drops waits at `reconnecting(attempt: 0)` without spending retries (on resume it reconnects at once at attempt 1), and the wait for a first connect's agent stops (the resume starts it again in full). Held time counts toward `CallRecord.duration`. (Refs #2)
- **Resuming after a phone call.** New `CallEngineConfiguration.resumesAfterSystemHold` (default true, no effect while `supportsHolding` is off): when iOS holds the call for another call (a hold the host did not request with `setOnHold(_:)`), the engine watches the device's calls through CallKit's call observer and, once every other call it saw during the hold has ended and none is left, asks CallKit to resume its call, which CallKit does not do for an app's calls. A third call still up keeps it held; a hold the host requested, or asked to keep with `setOnHold(true)`, is never resumed by the engine. In `ConduitCallEngineTesting`, `SimulatedCallSystem.startOtherCall()`, `setOtherCallHeld(_:onHold:)`, `endOtherCall(_:)` and `otherCallIDs` simulate other calls on the device.
- **A resume CallKit does not follow with an audio activation.** After a phone call on iOS 27, resuming the engine call from the app did not bring CallKit's activation, so the call was not held, had no audio, and nothing recovered it. When a resume finds the session not activated, the engine waits 2 seconds, then holds and resumes the call through CallKit again (silently: no `isOnHold` change, cue or signal), up to 3 times per resume, stopping at the activation, a hold, or the call's end; a hold asked for meanwhile stands. Before fulfilling a resume while the session is not activated, the device provider also sets the session's category and mode again, without activating it, and logs the session as it was. While another call is still active the engine does not ask, and no longer spends one of its three requests on that: it checks again every 2 seconds for up to 30 seconds and asks at once when that call ends (a phone call was still listed 2 seconds after it was hung up, and the call sat without audio). New `SimulatedCallSystem.EngineTimer.activationRecovery` for the wait; `holdRequests` lists the pairs.
- **A hold stops the first connect's join deadline**, so a call held while it waits for its agent does not fail as `.agentUnreachable` with the user on another call; on Daily it otherwise always would, because a held call's agent audio is unsubscribed and Pipecat's Daily transport sends client-ready only for playable audio.
- **Held calls are silent on both adapters.** On `PipecatDailyTransport` a detach that follows an attach now unsubscribes from the agent's audio (Daily has no playout control), the next attach subscribes again and returns once Daily has applied it (within 2 seconds, so a `call-resumed` sent after it reaches an agent the user can hear), and a held call that reconnects joins unsubscribed. A call that is never detached keeps Daily's default subscription. `LiveKitTransport` already stopped playout and capture on detach; it now logs the audio engine's state on attach, detach and connect. In-app hold and resume restored Daily's audio on a device; that the agent is silent during the hold is verified in unit tests only. (Refs #2)

### Behaviour changes

Beyond the breaking changes above, these change what a host can observe:

- The mic opens once the call is connected, not at CallKit's activation. CallKit activates an outgoing call's audio before the credential fetch and the join, and 0.1 opened the mic then (a no-op on most SDKs before the join, but audible to an agent already in the room, and it picked up a host's ringback). The engine now sends `setMicEnabled(false)` at such an activation and `setMicEnabled(true)` when the call connects; a call that connects before the activation opens it at the activation, as before. A host no longer needs to withhold the mic through its ringback.

- `.moment(.connected)` waits for CallKit's activation of the call's audio. A pre-connected ring answered with its agent there, and any call that connected before the activation, delivered it at the state change, into a session that was not live. It now comes once the call is connected, CallKit has activated its audio and it is not held, whichever is last: with the transition when the session is already active, otherwise at the activation (or the resume), with no state change. A call that drops before it was delivered gets `.moment(.connected)` instead of `.moment(.reconnected)` when it is back.
- Route work waits for CallKit's activation on every call. While the session is not activated (before the first activation, and after a deactivation until the next), the engine reads no routes, applies no hands-free default and ignores `selectAudioDevice(_:)` (which used to reach the transport); the activation refreshes the list and, for a connected call, applies the default.
- An audio activation that arrives while a ring is unanswered is ignored: CallKit activates an incoming call's session only once its answer action is fulfilled, so it belongs to an earlier call. An activation after CallKit delivered the answer action, before the engine has handled it, still counts.
- With pre-connect: a ring answered with its pre-connected agent there goes `incomingRinging -> connected`, with no `.connecting`; `makeTransport` can be called twice for one call (for the ring, and at the answer if the preparation failed), so it must return a new transport each time; and with `.media` requested by the push and the target, the transport is created during the ring even when it then declares it cannot join. A ring's credential failure after the answer used to fail the call at once; it now makes one `.answered` request first.
- After an interruption that ends without `shouldResume`, and before CallKit activates the session again, `isInterrupted` stays true (it went false while the mic stayed closed); an unmute or a push-to-talk press reopens the mic. `isInterrupted` is a computed property.
- CallKit activating the audio of a call that is not held ends an interruption by itself, as does resuming a call whose audio CallKit activated during the hold. An activation during an interruption used to keep the mic closed until the interruption's end was reported, and after a phone call iOS 27 never reported it, so a call taken back from a phone call stayed "interrupted" with its mic closed for the rest of the call. An end without `shouldResume` still does not reopen the mic by itself.
- Once `startPushRegistration()` has run, the engine keeps itself alive for the rest of the process (its PushKit registry holds it strongly), so a push is always reported even if the host releases it. (#17)
- The debug and info log lines of a release build of the package are filtered at runtime instead of compiled out (by default still not delivered), so `CallEngineLog.minimumLevel = .info` brings them back.

### Fixes

**Engine**

- The mic is gated on audio activation and interruptions on every path, and follows one rule whatever order its inputs arrive in. `setMuted(false)`, an unmute from the system UI and `setPushToTalkActive(true)` used to open the mic at once, even before CallKit activated the session or during an interruption, and if CallKit activated the session again during an interruption that then ended without `shouldResume`, the mic stayed closed for the rest of the call while `isMuted` was false. Now every input (activation, deactivation, an interruption's start and end, in-app and system mute, push-to-talk, the transport reporting `.connected`) re-derives the mic, the engine's attach, detach and mic commands reach the transport one after another in the order they were issued, a deactivation turns the mic off before detaching, and a transport that reports `.connected` before CallKit activated gets `setMicEnabled(false)`. A push-to-talk button still held when the session activates or an interruption ends opens the mic. (#19)
- The engine no longer waits indefinitely for a transport that reports `.reconnecting`: after 30 seconds (the backoff cap) without `.connected` or `.disconnected`, it runs its own reconnect on the same transport instance, without `disconnect()`, from `reconnecting(attempt: 0)` to `reconnecting(attempt: 1)`. With the bundled adapters such an attempt does not rejoin a session the SDK is still healing (each throws and spends a retry, and the SDK's own recovery still decides), so only a heal that outlasts the whole budget ends the call as `.lostConnection`.
- A reconnect attempt whose transport joins but never reports `.connected` no longer leaves the call in `reconnecting(attempt:)` for good (`joinTimeout`, above).
- A lost call-control signal is no longer permanent: an agent that closed its audio on `call-held` stayed closed for the rest of the call if that one message was lost. Signals are now retried (above).
- When a reconnecting call recovers or is held while an engine attempt is inside the transport's `connect(_:)`, the engine no longer cancels that connect's task (it still cancels an attempt waiting out its backoff or fetching credentials, and ignores the outcome of a connect it leaves running). Cancelling could abandon the very session the call had just counted as connected: an SDK join that honours task cancellation, as LiveKit's does, cleans the room up.
- `TransportError.authenticationFailed` during a reconnect attempt (from the target's `connect` or the transport's), and an `.error(.authenticationFailed)` event while reconnecting, fail the call at once as `.badToken`; they were retried until the budget ran out and the call failed as `.lostConnection`. (#11)
- Audio activation is tied to the call in progress: an activation with no call in progress (from a call that ended while dialing) is ignored instead of being replayed onto the next call's transport, `isAudioActivated` is cleared when a call ends, and deferred work started by an activation, a deactivation, a mute, an interruption or a route change acts on the transport that was live when it started and stops if that call has ended. (#9)
- Ring-status receipts are sent only for targets the delegate resolves; a push for an unknown target used to POST to its push-supplied `status_url`. For a push during another call, `targetForIncomingCall` is now asked whether or not CallKit accepted the report. (#8)
- A push carrying the `call_id` of the call that is ringing or in progress is a duplicate delivery: it is reported to CallKit, as PushKit requires, and otherwise ignored. It took the busy path, producing a missed-call record and a `busy` receipt for a live call. (#7)
- A ring CallKit refuses because it already holds a call with that id is no longer ended in CallKit (that would end the call CallKit holds); it is still recorded as failed with `.unknown`.
- CallKit answer and mute actions apply only to the call they name. An answer for a busy ring answered the ringing call, and a mute for another call's id muted the live one. (#6)
- A CallKit provider reset ends the call the way any other failure does, so transition-driven sounds stop (above). (#5)
- A ring that cannot proceed (unknown target, or refused by CallKit for a reason other than Focus) no longer puts a failure screen up for a ring the user never answered (above). (#4)
- A call's `.ended(outcome)` always matches its record (above). (#1)
- An event a ring's transport had already sent when the ring ended straight back to `.idle` (timed out, withdrawn, a provider reset) no longer reaches the live-call path, where the agent leaving or rejected credentials produced an `.ended` or `.failed` state with no call behind it. Events from a transport that is no longer the call's, and any event with no call in progress, are ignored.

**Transport adapters**

- Both adapters deliver call-control signals: `send(_:)` carries each `CallSignal` as the end-call signal's RTVI client message with the signal's raw value as `t` (`{"id": "<8 characters>", "label": "rtvi-ai", "type": "client-message", "data": {"t": "call-held"}}`; Daily's also carries `"d": null`, as its end-call signal always has), and reports what became of it. `LiveKitTransport.send(_:)` returns `.sent` once LiveKit took the message on its reliable data channel, and `.failed` when the room was leaving or gone, the publish failed, or its 2-second bound ran out. `PipecatDailyTransport.send(_:)` sends through the Daily call client's `sendAppMessage(json:to:)` in the form that reports Daily's result, and returns `.sent` once Daily has sent it and `.failed` before the join, after `disconnect()` or when Daily refuses it. (Refs #2)
- Both adapters can join while a call rings (`canConnectWhileRinging` is `true`), so both take pre-connect's `.media` tier. `LiveKitTransport` touches no audio before the attach. `PipecatDailyTransport`, whose SDK manages the audio session itself, unsubscribes from the agent's audio before a ring's join (`connectWhileRinging(_:)`) and subscribes at the first attach, after the answer, returning once Daily has the subscription; the bot cannot report ready while unsubscribed (Pipecat sends client-ready only for playable audio), so for a join made before that first attach the bot being in the room counts as ready: the ring's own join, and any later join on that transport before the first attach (a reconnect, or the answered call's connect after a failed preparation, before iOS activated the audio). A join while the transport is detached after an attach (a held call that reconnects) joins with the agent unsubscribed, and its bot gets ready once the resume's attach subscribes it. Every other Daily join (an outgoing call, an answer that joins after the ring, a reconnect of a call that is attached) keeps Daily's default subscriptions and waits for bot-ready. Observed on one phone (iPhone 17, iOS 27.0, locked, app not running): Daily rings of up to 20 seconds, one with a cold launch by the push, were silent and the answered calls played the agent cleanly with the route settled within about 0.3 seconds, where a join with default subscriptions during the ring left the call with no agent audio and the route flipping; a LiveKit ring joined silently and was connected at the answer.
- Both adapters treat a connect attempt as over once it has reported a disconnect, its connect has thrown, or the host has called `disconnect()`, and report nothing that would steer the engine after that. A late callback from a dropped call used to be judged as part of a live one: on LiveKit a late participant-left could end a reconnecting call as `.completed`; on Daily a late bot-left could do the same, a late bot-ready could report a dead attempt as connected, and a failed reconnect attempt was counted twice. Neither adapter reports `.connected` after the host's `disconnect()`. ([#10](https://github.com/AmirAlsad/ConduitCallEngine/issues/10))
- Both adapters remove credentials and URL queries from the SDK error text they put in a `TransportError`. (#18)
- `PipecatDailyTransport` sends its client messages, the end-call signal included, once the Daily call is joined, through the Pipecat transport's Daily app message; `PipecatClient.sendClientMessage` refused until the bot reported ready, so a hangup before that sent no end-call signal and the agent waited out its grace window.
- `PipecatDailyTransport.disconnect()` releases its Pipecat client after the end-call signal and the leave. It never did, so every Daily call left Pipecat's `DailyTransport` and its Daily `CallClient` alive for the rest of the process (pipecat-client-ios-daily 1.3.0 breaks that cycle only in `release()`). A `connect` after `disconnect()` builds a fresh client, and one that starts while a `disconnect()` is still flushing its end-call signal gets its own.
- `PipecatDailyTransport.connect(_:)` no longer breaks a call Daily is healing. When the engine reconnects on the same transport while the Pipecat client is still in the call, Pipecat refuses (`BotAlreadyStartedError`), and the adapter used to reset its connection state and stop watching the network path first, so the path coming back or Daily recovering went unreported and the call ended as `.lostConnection` after Daily had healed. Such a connect now changes nothing: it reports `.connected` if the call is connected and the path is up, and otherwise throws `.connectionFailed` with the path watch still running. A connect that arrives while an earlier join is still waiting for the bot no longer swallows that join's bot-ready.
- `PipecatDailyTransport.connect(_:)` takes over a session whose bot never got ready instead of refusing it (after a reconnect attempt's join deadline ran out, or at the resume after a held reconnect): it leaves the stale session without the end-call signal, releases its client, and joins with a new one. It used to refuse, so every remaining attempt threw, each stranding a newly started agent on a backend that starts one per request. A call Daily is healing is still refused.
- `PipecatDailyTransport` keeps a call on the route it starts on. With no preferred device, Daily's SDK configures the session for video chat (the loudspeaker) when it joins and after every change to its inputs, and such a change also resets a device set only as Daily's preferred device (all `setAudioDevice(_:)` did, through Pipecat's `updateMic`), for instance when the mic opens. A call CallKit started on the earpiece moved to the loudspeaker while it connected (observed on an iPhone 17 with iOS 27.0), and a route picked in the app could be lost the same way. At the first attach the adapter now reads the route the session is on and asks Daily to prefer it, both as Daily's preferred audio device and as its microphone input's device, before the join when CallKit activated first; every join's settings name it, and a new Daily client is given it before its join. The engine's `setAudioDevice(_:)` wins over it and is kept for later joins of the transport. While nothing was asked for, a Bluetooth or wired device that connects during the call is followed, and when it goes the call returns to the earpiece (or another headset). Car audio, AirPlay and USB routes are left to Daily. `selectedAudioDevice()` reports the microphone input's device, so it names the route asked for. The adapter logs the route read at the activation, each request with Daily's answer, and Daily's devices after the join. Observed on one phone (iPhone 17, iOS 27.0): an outgoing call stayed on the earpiece, or on AirPods. A ring joined before the answer was still answered on the loudspeaker, because Daily's join had configured the session before CallKit's activation and the attach kept what it read; so a join that starts before the first attach (a ring's, or credentials that arrive before the activation) now starts on a provisional route read just before it, a connected Bluetooth or wired device or else the earpiece, never the loudspeaker. It is given to Daily as its preferred audio device only, which Daily keeps without touching the session until its join, and the join's microphone input names it. A ring's join is asked nothing else before the first attach; the engine's request waits for it. At the first attach after such a join a headset reading is followed, and a loudspeaker reading, which only Daily can have chosen, gives the earpiece; the engine's request still wins. The adapter logs the provisional choice (`Daily route before activation: …`). The join-first case is not yet verified on a device; see the Daily notes in the Integration Guide for what to look for.
- `ConduitCallEngineDaily` declares its dependency on Daily's `Daily` product (`daily-client-ios`, from 0.38.0, the floor `pipecat-client-ios-daily` already sets), which it imports directly. Nothing resolves differently.
- The LiveKit dependency floor is 2.18.0 (was 2.15.1): from 2.18.0 every reconnect LiveKit gives up on ends with the room disconnected (client-sdk-swift PR #1144); before it, a failed full reconnect could be reported as complete with the room still marked connected, and the call could show connected with no audio. A server-ordered full reconnect whose media connection times out is now retried by LiveKit and then reported as a drop. The adapter no longer disconnects the room itself after a completed reconnect. ([#20](https://github.com/AmirAlsad/ConduitCallEngine/issues/20))
- A LiveKit reconnect that rejoins a room with no remote participant ends the call as the agent's hangup (`.disconnected(.botLeft)`, so `ended(.completed)`), instead of reporting a drop that made the engine run the target's `connect` again and, on a typical backend, start a fresh agent session inside the same call. A full reconnect's own participant cleanup is not mistaken for the agent leaving (LiveKit reports it with the agent still listed). ([#21](https://github.com/AmirAlsad/ConduitCallEngine/issues/21))
- `LiveKitTransport.connect(_:)` no longer rejoins a room LiveKit is still reconnecting. `Room.connect` would clean the room up, ending LiveKit's reconnect state without cancelling its reconnect task, which the adapter took as a drop of the new attempt, and the surviving task could later mark the room connected while the next join was under way, after which that join never reported `.connected`. Such a connect now throws `.connectionFailed` and leaves LiveKit's reconnect to report its outcome; a room that has already healed with the agent present is reported `.connected`; a reconnect completion that arrives before the current attempt's room has connected is ignored.
- `LiveKitTransport` owns its joins. `Room.connect` cleans up and sets up before the room reports `.connecting`, and `Room.disconnect` does nothing while the room is `.disconnected`, so a `disconnect()` in that window (a ring declined, or a call ended, just as the device started joining) left the device in the room with the agent. `disconnect()` now lets a join in flight finish (within its 2-second bound) before it signals and leaves, and a join it could not wait for leaves the room, with the end-call signal, when it completes. A `connect(_:)` while an earlier join was still in flight started a second `Room.connect` on the same room, each one's cleanup tearing the other down; it now cancels the earlier join and waits for its cleanup, and of two connects waiting for the same join only the newer one joins.
- `LiveKitTransport` reports `.disconnected(reason: .botLeft)` when the last remote participant leaves this attempt's room after it started connecting and before the agent was reported ready (an agent that came with LiveKit's join response and left). It reported nothing, so a pre-connected ring kept a room with no agent and a call waited out `joinTimeout`; such a call the user placed now ends as `.noAnswer` at once. A join the transport supersedes no longer reports its room's participants leaving as the agent's hangup.
- `LiveKitTransport.disconnect()` sends the end-call signal whenever the room is not already leaving, not only once it reports connected, letting an in-flight connect finish first and bounding the whole signal at 2 seconds. A host that disconnected during a connect or one of LiveKit's own reconnects sent nothing. ([#22](https://github.com/AmirAlsad/ConduitCallEngine/issues/22))
- `LiveKitTransport` publishes its client messages reliably; the end-call signal used LiveKit's lossy default.
- `LiveKitTransport` classifies a connect error as `.authenticationFailed` only on an exact signal: LiveKit's validation request answered 401 or 403 (a `.validation` error whose message starts `HTTP 401:` or `HTTP 403:`), or LiveKit's insufficient-permissions error. It searched the error's whole description, which includes nested errors' user info such as the failing WebSocket URL, so a plain network failure could match by chance, and a server host name containing "token" always did; with `.authenticationFailed` now ending a reconnecting call at once, a false match would end a call that only needed a retry.
- Both adapters' test targets now run the real adapter under a simulated engine, against Pipecat and Daily fakes whose readiness depends on the agent's audio subscription and a LiveKit room double that sequences its work as `Room` does.

**Documentation**

- The Integration Guide has a section for agent developers, "When your agent should start speaking": greet on `call-connected`, not when the session connects, for a client that lists it in `call_signals` (in its credential requests and its push registration), with a fallback grace period for a lost one. The push contract says that the `answered` receipt is sent at the answer, before iOS activates the call's audio, so it always precedes `call-connected`, and is only that fallback for a ring. It says prominently to compare receipt `call_id`s case-insensitively, and that a server sending no `ring_timeout` must assume a ring can last indefinitely.
- `ConnectRequest.callID` states the engine's guarantee: never nil for `.answered` and `.ringing(joinsBeforeAnswer:)`, always nil for `.outgoing`, and for `.reconnect(attempt:)` nil exactly for an outgoing call.

### Known limitations

- **A phone call the user accepts ends the call.** With holding off (the default), as in 0.1, accepting or placing a phone call during an engine call ends it. Keeping the call through a phone call needs the experimental hold, which does not yet bring the audio back afterwards (above).

## 0.1.0 - 2026-11-11

- Initial extraction of the call engine from the Conduit iOS app. `ConduitCallEngine` provides `CallEngine`, which reports calls to CallKit, receives agent-initiated calls over PushKit VoIP pushes, runs the call state machine, owns the call's audio-session policy and reconnects after drops, driven by host-supplied `CallTarget` values and reporting back through `CallEngineDelegate` and `CallRecord`. It also sends optional ring-status receipts and defines the `CallTransport` protocol.
- `ConduitCallEngineDaily` (`PipecatDailyTransport`, Daily through the Pipecat iOS client) and `ConduitCallEngineLiveKit` (`LiveKitTransport`, native LiveKit with manual audio) adapters, shipped as separate products so the core links no WebRTC SDK.
- `ConduitCallEngineTesting`: `FakeTransport`, `SimulatedCallSystem` and `CallEngine.simulated(...)` for the iOS Simulator and host unit tests.
- `PipecatDailyTransport` reports short network interruptions: while connected, losing the device's network path emits `.reconnecting` (the call shows `reconnecting(attempt: 0)`) and getting it back emits `.connected`, as LiveKit's own reconnects already did. Daily heals these inside its SDK without telling the Pipecat client, so they were silent before. The signal is the network path, not Daily's media state.
- `LiveKitTransport` no longer reports a call connected after LiveKit abandons its own reconnect. A completed SDK reconnect now counts only if the room is connected and a remote participant is present; otherwise the adapter disconnects the room and reports `.disconnected(.networkDropped)`, so the engine's reconnect and retry budget apply. Previously a long outage could leave the call showing connected with no audio and no further recovery.
